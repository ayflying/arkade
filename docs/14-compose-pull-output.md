# 编排更新镜像与「更新部署」

编排操作窗口里有两个不同的事情，别混：

- **更新镜像**（`pull`）：只执行固定的 `docker compose pull`，不执行 `up`、不自动重建运行中容器。镜像拉到本机了，容器仍跑旧版本，需要用户另行启动。
- **更新部署**（`deploy`）：先判断有没有新版本，**只有确实有更新才拉取并重建对应服务**；没有可更新的镜像时不拉取、也不重建任何容器。

界面上的主按钮是「更新部署」，因为用户真正想要的就是"有新版本就更新，没有就别动"。`pull` 保留为纯拉取动作（不占主按钮位）。

## 更新部署的判定流程

```
1  docker compose ps --format json -a     读本机容器及其镜像 ID / 摘要（输出不展示）
2  docker manifest inspect <引用>          只查远端元数据，不在本机产生镜像（输出不展示）
3  docker compose pull <有更新的>          只拉有更新的；任一失败立即停止
4  docker compose up -d <该服务>           只重建确实换了内容的服务
5  docker compose up -d --force-recreate  仅当远端身份查不到、但拉取确实引入了新内容
```

判定规则（逐条对应 `deploy_test.go` 里的用例）：

| 情形 | 结论 |
| --- | --- |
| 本机 `RepoDigests` 已含远端 digest（按"仓库@摘要"比对） | 已是最新，不拉取、不重建 |
| 远端只给镜像 ID 且等于本机容器镜像 ID | 已是最新，不拉取、不重建 |
| 本机没有该引用对应的容器 | 需要更新（首次部署交给 `up`） |
| 查不到远端清单（私有仓库未登录 / 离线 / 镜像已删除） | 无法判定，**不进入**拉取列表 |
| 全部引用都查不到 | 退化为"只拉取、按拉取后的实际内容判断"，并在日志里明说 |
| `image:` 里含 `${...}` 插值 | 无法判定（真实引用要由 compose 求值），不拉取、不重建 |

铁律：

- 没有新版本时**一条写命令都不执行**——不会因为"点了一次更新"而白停一次服务。
- 拉取失败**立即停止**，绝不继续重建。"拉取失败却用旧镜像重建"会让服务白停一次，而用户以为已经更新。
- 不声称"已是最新"除非有证据。查不到远端摘要时只能说"无法在拉取前判断"。
- `up` 失败时用本机原有镜像重试一次；回滚也失败则如实报失败，不假装成功。

## 输出与完成提示

实现采用异步启动与每秒增量游标读取，而不是等待同步 HTTP 请求结束才显示整段日志。输出仅在进程实际写出后出现：项目锁排队、下载器缓冲或网络等待期间可以没有新行，不能填充虚假进度。

- 第 1、2 步是**要解析的结构化输出**（`ps` 的 JSON、`manifest` 的清单），不进入日志：它们会吃光单任务 2000 行 / 256 KB 配额，把真正的拉取失败信息挤掉。用户通过阶段说明知道"正在检查什么"。
- 第 3 步之后的拉取/重建输出**完整展示**（已脱敏、有上限）。
- 任务进入终态后，窗口底部显示完成横幅：成功是「更新完成，如日志无异常再关闭此窗口！」，失败是「执行失败，请先按上面的日志排查后再关闭此窗口。」横幅只由任务状态驱动，**不解析日志文本**；服务端同时回传 `updated_services`（机器可读结论），界面据此显示"本次更新了哪些服务"或"没有更新任何服务"。

## 权限与安全

- 启动与读取都需要该服务器 operate 权限，配置管理权限不因此下放。
- 只执行白名单动作与固定命令，不支持任意命令输入，不通过 shell 解释。
- 请求正文只包含幂等请求标识与动作名，任务输出不写入审计。审计记录"提交拉取任务"，不把 HTTP 202 受理当作镜像更新成功。
- 日志经 Agent 脱敏后返回；浏览器仅按文本展示，禁止 HTML 解释。输出缓冲、任务数量和保留时间均有上限。
- 返回结果禁止缓存，游标只返回新增内容，截断必须明确提示。

## 中断与重试

关闭窗口或网络中断不会取消已接受的任务，重开窗口继续读取；发起请求结果不明确时，使用同一 `request_id` 重试确认，不能生成新任务冒险重复执行。断线不等于执行失败或成功，最终结果必须由 Agent 任务状态确定。Agent 进程重启后临时任务记录可能丢失，界面应明确无法读取而非猜测成功。
