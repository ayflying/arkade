# 05 已决策项（决策记录）

本文记录已经**明确拍板**的决策，与 01-04 的探索性内容区分开。后续开发以本文为准；如需变更，先在此处补一条带日期的变更记录，再改实现。

## D-01 首期容器引擎：Docker + Podman

- 首期只实现这两个运行时，统一收敛到「运行时抽象层」（见 03 技术选型）。
- containerd / LXC 等后续再评估，不预留未实现的空壳接口。
- **注意**：Podman 与 Docker 的用户态差异必须显式处理——无守护进程、rootless、卷与网络创建方式不同、部分 Compose 指令不受支持。同一份 Compose 在不同引擎上的实际结果**不承诺完全一致**，遇到目标引擎不支持的配置必须报错解释原因，禁止静默忽略。

## D-02 编排格式：完全兼容 Compose

- Hub 与 Agent 都按标准 Compose 规范解析与执行，用户无需改写成 Arkade 专用格式。
- Arkade 自有元数据（来源、版本、权限、负责人等）**单独存表**，不写进用户的 Compose 文件，保证文件可原样带走。
- 部署完整性包含：主 YAML、相对路径挂载、`env_file`、多文件 `-f` 叠加、扩展字段与 `secrets/configs` 引用。**只存一份 YAML 不算存了完整部署**。
- 支持程度的验收以「目标引擎的 Compose 能力」为准，不支持项在保存与部署前给出明确提示。

## D-03 Hub 存储：首期 SQLite，单实例

- 首期按**单个 Hub 实例 + 本地磁盘存储**设计，不提前做多实例部署与多数据库适配。
- 使用 SQLite（WAL 模式），连接参数按「单写连接 + 只读连接池」配置，避免 `database is locked`。
- 业务层禁止直接使用 SQLite 专有语法（如 `AUTOINCREMENT`、`INSERT OR REPLACE`），迁移脚本通过统一的迁移器按版本顺序执行，便于后续切换 PostgreSQL。
- 提供数据库文件的定时备份落地口径（备份即复制 `*.db` 一致快照 + 校验）。
- **变更记录**：后续若要上 PostgreSQL，需重新评估迁移器与连接池策略。

## D-04 用户体系：多用户 + 用户组

- 用户可加入多个用户组；组绑定**可访问的服务器范围**。
- 权限三档：查看 / 操作 / 管理，权限按「组 × 服务器」授予，取并集。
- 后端强制校验（每个接口都过鉴权中间件），前端隐藏按钮只是体验优化，**不作为安全边界**。
- 管理档权限才能改 Agent、凭据与用户组配置。

## D-05 Agent 离线管理入口：首期做本地 CLI

- Hub 不可用时，SSH 登录服务器用 `arkade-agent` 本地命令查看、启停容器与本机编排；直接使用原生的 `docker` / `podman` / `docker compose` 能力始终保留。
- 首期**不做** Agent 自带网页管理页（避免每台机器额外暴露端口与身份验证面）。
- **变更记录**：如后续确有需求，再单独立项 Agent 内置 Web 控制台。

## D-06 迁移允许停机，优先数据一致

- 迁移流程固定为：预检 → 停源服务 → 传输镜像与卷 → 起目标服务 → 校验。
- **源端保留**：校验通过后由用户显式确认再清理源端，避免迁移失败无退路。
- 失败回滚：先确保目标侧容器已停止并清理，再恢复源端容器；禁止两端同时写同一份数据。
- 不做「在线热迁移」的伪实现，不承诺零停机。

## D-07 传输路径：直连优先，不通走 Hub 中转

- 两台被管理服务器**不保证互通**（Agent 本就为 NAT/内网后设计）。
- 直连可用时点对点传输；不可用时经 Hub 中转。
- 大文件（镜像层、卷数据）与控制信令分离，走独立流式 HTTP/2 通道；HUB 中转需限制磁盘占用与带宽，超限中断并报错，不静默丢弃。

## D-08 技术栈：Hub/Agent 为 Go，前端 Vue 3

- Hub/Agent 均为 Go，单个静态二进制，运行时抽象层共用。
- Hub HTTP 采用标准库 `net/http` + `chi` 路由 + `gorilla/websocket`，**不引入 GoFrame**；连接层与消息路由保持标准库写法。
- 前端 Vue 3 + `<script setup>` + TypeScript + Vite + Pinia；组件库首期用 Naive UI（按需引入）。
- 实时状态经 WebSocket 推送，不做轮询。
