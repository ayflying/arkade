# 05 已决策项（决策记录）

本文记录已经**明确拍板**的决策，与 01-04 的探索性内容区分开。后续开发以本文为准；如需变更，先在此处补一条带日期的变更记录，再改实现。

## D-01 首期容器引擎：Docker + Podman

- 首期只实现这两个运行时，统一收敛到「运行时抽象层」（见 03 技术选型）。
- containerd / LXC 等后续再评估，不预留未实现的空壳接口。
- **注意**：Podman 与 Docker 的用户态差异必须显式处理——无守护进程、rootless、卷与网络创建方式不同、部分 Compose 指令不受支持。同一份 Compose 在不同引擎上的实际结果**不承诺完全一致**，遇到目标引擎不支持的配置必须报错解释原因，禁止静默忽略。

## D-02 编排格式：完全兼容 Compose

- Hub 与 Agent 都按标准 Compose 规范解析与执行，用户无需改写成 Arkade 专用格式。
- Arkade 自有元数据（来源、版本、权限、负责人等）**单独存表**，不写进用户的 Compose 文件，保证文件可原样带走。
- 部署完整性包含：主 YAML、相对路径挂载、`env_file`、多文件 `-f` 叠加、扩展字段与 `secrets/configs` 引用。**只存一份 YAML 不算存了完整部署**。
- 支持程度的验收以「目标引擎的 Compose 能力」为准，不支持项在保存与部署前给出明确提示。

## D-03 Hub 存储：首期 SQLite，单实例

- 首期按**单个 Hub 实例 + 本地磁盘存储**设计，不提前做多实例部署与多数据库适配。
- 使用 SQLite（WAL 模式），连接参数按「单写连接 + 只读连接池」配置，避免 `database is locked`。
- 业务层禁止直接使用 SQLite 专有语法（如 `AUTOINCREMENT`、`INSERT OR REPLACE`），迁移脚本通过统一的迁移器按版本顺序执行，便于后续切换 PostgreSQL。
- 提供数据库文件的定时备份落地口径（备份即复制 `*.db` 一致快照 + 校验）。
- **变更记录**：后续若要上 PostgreSQL，需重新评估迁移器与连接池策略。

## D-04 用户体系：多用户 + 用户组

- 用户可加入多个用户组；组绑定**可访问的服务器范围**。
- 权限三档：查看 / 操作 / 管理，权限按「组 × 服务器」授予，取并集。
- 后端强制校验（每个接口都过鉴权中间件），前端隐藏按钮只是体验优化，**不作为安全边界**。
- 管理档权限才能改 Agent、凭据与用户组配置。

## D-05 Agent 离线管理入口：首期做本地 CLI

- Hub 不可用时，SSH 登录服务器用 `arkade-agent` 本地命令查看、启停容器与本机编排；直接使用原生的 `docker` / `podman` / `docker compose` 能力始终保留。
- 首期**不做** Agent 自带网页管理页（避免每台机器额外暴露端口与身份验证面）。
- **变更记录**：如后续确有需求，再单独立项 Agent 内置 Web 控制台。

## D-06 迁移允许停机，优先数据一致

- 迁移流程固定为：预检 → 停源服务 → 传输镜像与卷 → 起目标服务 → 校验。
- **源端保留**：校验通过后由用户显式确认再清理源端，避免迁移失败无退路。
- 失败回滚：先确保目标侧容器已停止并清理，再恢复源端容器；禁止两端同时写同一份数据。
- 不做「在线热迁移」的伪实现，不承诺零停机。

## D-07 传输路径：直连优先，不通走 Hub 中转

- 两台被管理服务器**不保证互通**（Agent 本就为 NAT/内网后设计）。
- 直连可用时点对点传输；不可用时经 Hub 中转。
- 大文件（镜像层、卷数据）与控制信令分离，走独立流式 HTTP/2 通道；HUB 中转需限制磁盘占用与带宽，超限中断并报错，不静默丢弃。

## D-08 技术栈：Hub/Agent 为 Go，前端 Vue 3

- Hub/Agent 均为 Go，单个静态二进制，运行时抽象层共用。
- Hub HTTP 采用标准库 `net/http` + `chi` 路由 + `gorilla/websocket`，**不引入 GoFrame**；连接层与消息路由保持标准库写法。
- 前端 Vue 3 + `<script setup>` + TypeScript + Vite + Pinia；组件库首期用 Naive UI（按需引入）。
- 实时状态经 WebSocket 推送，不做轮询。

## D-09 编排内容两边都存，同步单向

- Hub 存数据库（权威副本，可展示/编辑），Agent 存本机 `stacks/<name>/compose.yml`（保证 Hub 不可达时仍能独立运行）。
- 同步方向固定为 **Hub → Agent 单向**：内容随请求下行，上行只传状态与哈希。因为只有一个写方向，不存在双向写冲突。
- 「是否一致」靠比对两边哈希判断（`drift` 字段），不做数据库级同步。
- **远端哈希为空时不算 drift**：那表示「还没下发成功」，不是「被人篡改」。误报会让用户以为配置被人动过。
- 创建/更新的顺序是**先写库、再下发**：下发失败不回滚、不删记录，用 `sync_ok` / `sync_hint` 表达。用户写的几十行编排不能因为一台机器临时离线就丢掉。
- 删除的顺序**相反**（先删机器、再删记录）：若先删记录而 Agent 失败，会留下「界面看不见但还在跑、还占端口」的编排，彻底无法管理。

## D-10 请求超时按方法分档

- 默认等待 15 秒（列容器、启停、查日志等快操作）。
- 编排类操作单独放宽：`compose.up`/`compose.pull` 11 分钟、`compose.rebuild` 12 分钟、`compose.down`/`compose.remove` 2 分钟、`compose.backup` 5 分钟。
- 数值取 Agent 侧命令超时再留余量，保证 Agent 能先把明确的错误（YAML 写错、端口冲突）报回来，而不是 Hub 先超时。
- **为什么必须分档**：统一 15 秒会产生最尴尬的结果——Hub 已报超时失败，Agent 那边仍在正常执行并最终成功，用户看到「失败」但服务其实起来了。反过来把默认值整体调大同样有害：真正的卡死要拖十分钟才报错。
- `internal/agentlink/agentlink_test.go` 用测试钉死「慢操作超时必须大于默认值」与「快操作必须用默认值」，防止被改回。

## D-11 错误码区分「状态冲突」与「依赖不可用」

- `conflict` → HTTP 409：请求与目标当前状态冲突，**原样重试永远失败**，要引导用户改条件（如先停止容器）。
- `runtime_failed` → HTTP 503：依赖暂时不可用（引擎返回 5xx、套接字连不上），稍后重试可能成功。
- 两者混用会让前端只能显示含糊的「操作失败」：用户点多少次都没用，却被告知「请稍后重试」。
- Agent 侧 `ErrContainerConflict`（删除运行中的容器）映射为 `conflict`，文案直接写明该怎么改。

## D-12 删除类操作一律「默认不删数据」

- 删除容器：`remove_volumes` 默认 false。
- 删除编排：`remove_volumes` 默认 false。
- 前端一律做成「默认不勾选的复选框」，勾选后追加红框警示说明数据永久丢失。
- 参数解析对非法布尔值（`=ture`、`=yes`）**报 400 而不是当 false**：静默按 false 处理会让用户以为卷已删除，宽松当 true 则直接丢数据。两种误判都不可接受。

## D-13 Agent 禁用与删除的语义

- **禁用**：在握手阶段拒绝连接，并回一条明确的错误信封再关闭（不是直接断开）。直接断的话 Agent 只能看到「连不上」，与网络故障无法区分，会无限重连且无从排查。禁用时若该 Agent 当前在线，主动踢下线——否则握手只对新连接生效，存量通道仍然可用。
- 握手时**先查禁用状态再写库**：顺序反了会让被禁用的机器每次重连都刷新 `last_seen`，界面上显示「刚活跃过」，运维无法判断禁用是否生效。
- **删除**只移除服务器记录及其专属接入凭据，**不删机器上的任何容器**，也**不连带删编排记录与组授权**。专属密钥随删除失效，不能再凭旧密钥重新注册；旧共享密钥接入的Agent可能重新注册，同身份才能重新关联保留配置，重新添加的记录不会自动认领。要保留记录并拒绝接入应使用禁用。不要与列表的 `orphans` 混淆，后者指「Agent 上存在但 Hub 未登记」的编排，方向相反。
- 握手时**保留用户改过的显示名**：不能用上报的 Hostname 覆盖 `name`，否则用户改的名字下次重连就凭空消失。

## D-14 前端必须能区分「已保存」与「已下发」

- 编排记录同时带 `updated_at`（用户在 Hub 改内容的时间）与 `synced_at`（真正落到机器上的时间，0 表示从未成功下发）。
- 两者差得大，基本就是「改了但没同步成功」，界面必须让用户查得到，否则会误以为线上已生效。
- 服务器离线时**允许创建和保存编排**：先写 Hub，恢复连接后用户可以手动重新下发。当前没有自动重试/自动上线同步机制，界面不得承诺自动部署。

## D-15 网页预建Agent服务器与专属密钥

- 这里的服务器是受管 **Agent节点**，不是HTTP/SOCKS网络代理。管理员在服务器列表预建记录，生成其专属密钥，部署Agent后绑定该记录，不重复创建。
- 每台节点独立的256位随机接入密钥，仅创建/重置响应展示原文，数据库仅存SHA256摘要；摘要不可反推出高熵密钥，不提供找回接口。
- 明文不进入列表、URL、审计、日志、浏览器持久化。敏感响应禁止缓存；关闭弹窗丢弃临时引用。宿主机`.env`负责部署注入，权限0600，YAML与程序配置不嵌入密钥。
- 身份由密钥所绑定的数据库记录确定，不信任Agent自己声明的ID。旧共享密钥兼容存量节点，但不得冒充专属记录。
- 新记录从未接入时显示`pending`（待接入），不同于曾连接后离线。Agent连接成功后变为在线；列表自动刷新关闭时需要手动刷新。
- 重置令旧凭据立即失效并关闭存量连接；握手最终校验、写库及上线登记，必须与重置/删除/禁用共用临界区，防止旧请求在撤销后继续上线或复活已删除记录。
- 接入密钥是身份凭据而非单次兑换码。多台机器不得共用；相同身份的连接替换行为沿用现有重连策略，泄露后应立即重置。生产使用WSS保护传输。
- 本批已通过本地真实API与WebSocket集成测试，以及243真实Docker Agent的预建绑定、ID持久化、重置和删除撤销验证。浏览器确认添加入口与表单；密钥弹窗完整交互尚仅模拟测试通过，不扩张验收结论。
