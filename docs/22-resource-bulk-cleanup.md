# 资源列表的批量删除与清理

2026-11-24 部署至 243 并完成真实接口与全量测试验收。三类资源：本地镜像、网络、存储卷。

## 为什么改成勾选 + 批量

原来每行一个「删除」按钮，一次只能删一个。真实用途是「清出一批没人用的资源」——构建残留的悬空镜像、编排建完就没再用的网络、跑完一次就没人挂的卷。逐个点几十次是这条路走不通的主要原因。

改成「左侧勾选 + 页头批量删除」后，单个删除仍然可用（勾一个再删），但风险要重新处理：

- **不可删的项不给勾选**。使用中的卷、有容器接入的网络、Docker 内置网络，`selection` 列的 `disabled` 直接返回 true。这样「能勾的都能删」成为一条可依赖的直觉，而不是勾完点了才知道失败。
- **原因必须能查到**。勾选灰掉后用户一定会问「为什么」，所以原因挂在同行的标签 `title` 上，而不是只存在于代码里。
- **全选只作用于当前页**。跨页累积选择看着方便，实际很危险：用户在第 1 页勾了几项、翻到第 3 页点「全选」，很容易以为只删当前页，结果把前面勾的也一起删了。
- **批量删除同一时刻只允许一个**，执行期间其它批量入口禁用，防止连点造成重复请求。

## 为什么不做后端批量接口

三个列表接口本来就返回全量数组，删除一个就是一次 DELETE，逐个发即可。新增批量接口要为中心加三条路由、还要设计「部分失败怎么返回」，而真正需要的信息——**哪一个没删掉、为什么**——逐个删除天然就有。批量接口很容易把「5 个成功 2 个失败」压成一句「批量删除失败」，那反而是退步。

失败不中止：跳过失败项继续删其余的，最后汇总成「成功 N 个，失败 M 个：<名字>（<原因>）」。中止会让用户重来一遍，还得自己猜是哪一个卡住了。无论成败都以服务端为准重新拉一次列表——部分失败时本地状态必然不一致。

## 清理：三类资源各自的严格规则

| 资源 | 可清理范围 | 为什么这么定 |
|---|---|---|
| 存储卷 | 未被任何容器使用 | 被引用的卷删不掉（daemon 拒绝），且很可能正在跑业务 |
| 网络 | 无容器接入且非 Docker 内置（bridge/host/none） | 内置网络删不掉；有容器接入的删了会断掉正在跑的业务 |
| 本地镜像 | **悬空**（无标签）且无容器引用 | 见下 |

镜像这条要特别说清：**已打标签但没有容器引用的镜像不是垃圾**。它们是你准备重新部署时要用的，清掉等于让「下次起容器」变成一次必然的重新拉取。悬空镜像则相反——没有任何标签能再引用到它，除了占磁盘没有别的用途。所以只清悬空。

清理按规则**扫全量**，不看当前页、不看当前勾选。确认框里列出将被删除的对象（超过 10 个折叠成「等共 N 个」）——用户对「一批」没有直觉，只有看到具体名字才知道怕。卷清理的确认文案另外提示「若其中有暂时停用容器的数据卷，请先不要清理」，因为那是这条规则唯一会误伤的边缘情况。

## 存储卷显示挂载到的容器

协议 `VolumeSummary` 新增 `containers`（使用该卷的容器名，按名字排序）。之前只有布尔 `in_use`，用户无法回答「这个卷到底谁在占着」，也就无法判断能不能清掉。

必须包含**已停止但未删除**的容器：daemon 不允许删除被引用（哪怕引用者已停止）的卷，只统计运行中的容器会让界面显示「未使用」但删除却失败。`in_use` 与 `containers` 同源，不接受任何一方另算一份。

容器名超过 2 个时折成「+N」，完整清单在 `title` 里。名字已去掉 daemon 返回的前导斜杠。

## 镜像批量删除不得静默强制

单个删除有引用镜像时，前端会让用户勾「强制删除」。批量删除如果自动降级成强制删除，就等于把一批有引用的镜像静默删掉——那些容器会集体起不来，而用户只勾了几行。

因此批量路径 `force` 默认 false，有引用的镜像被跳过并如实报告；要动它们必须显式勾选页头的「同时强制删除（N 个被引用）」。全被引用时给出可执行的下一步（勾选强制，或先删容器），而不是一句失败。

## 边界

- 前端逐个删除，没有后端批量接口；几十个资源时请求是串行的，等待可以接受。
- 清理不提供预览清单让你再挑一遍，只有确认框里的名单（当前约定的交互）。
- 浏览器真实点击（勾选、批量删、清理）未逐项验收，只有契约测试与 HTTP 接口层验证。
