# 已有Compose项目自动接管

## 行为

Hub后台在Agent上线后约2秒内开始检查，随后每轮完成后约30秒扫描一次。不依赖打开浏览器，不在GET接口中写库；兼容项目自动出现在已纳管列表，不再要求逐个粘贴配置。

自动流程只执行：读取来源配置 → 安全预检 → 保存Hub权威副本 → 将相同配置登记到Agent管理区。不会调用启动、停止、拉取、重建或删除，不改原始Compose文件。已成功登记的同名项目不重复导入；已有不同内容的记录绝不覆盖。失败会重试，页面显示接管情况与原因。

## 首版支持范围

- 根据Docker Compose写入的project/config_files/working_dir标签识别；项目各普通容器来源标签必须一致，一次性容器不参与。
- 单份配置、位于项目工作目录内部、Linux普通文件，最大1MiB；工作目录必须为明确项目目录，不能是根目录或系统目录。
- 复用既有导入安全扫描与Compose解析校验。多文件、外部env_file/build/configs/secrets/include、相对挂载、环境插值等暂不自动接管，页面展示原因；手动导入入口保留，不降低既有安全要求。
- 不读取.env，不执行原目录里的脚本。不尝试从docker run容器反向猜出Compose。
- 读取由无网络、无额外能力、只读挂载单个项目目录的临时助手完成。助手固定使用本地alpine:3.20镜像ID和当前Agent程序，不会自动拉取。共享并发上限2，总时限60秒；读取不跟随符号链接，拒特殊文件与多硬链接。

## 权限与信任边界

自动接管是服务器级后台策略，本批按用户确认默认启用；任何浏览者不需要点击按钮，也不能通过GET触发额外接管动作。配置可能含敏感信息，仅在Agent与Hub之间流转并保存到原有管理存储，不放入未纳管列表、原因或日志；查看正文继续沿用现有权限。

容器标签不是独立的权限证明：有Docker管理权限的人可以伪造标签，本来就拥有主机级能力。系统对标签来源仍做路径形态、禁止目录、配置归属及逐级不跟随链接检查，但不承诺对抗恶意宿主机管理员替换挂载源。助手不挂整个宿主根目录，不修改项目原文件。

## 验证记录

开发测试覆盖：成功登记与幂等、不覆盖已有内容、内容哈希不一致拒绝、阻塞项目不落库、Agent未完成接管不标记同步、同内容自动重试。Agent侧覆盖来源标签一致性、单文件限制、路径边界、符号链接与特殊文件拒绝、危险字段不回传正文。

真实243独立项目 `arkade-auto-adopt-verification` 已验收：由测试脚本先正常启动全新Compose项目，未调用任何导入预览或接管接口，仅等待后台扫描即自动登记成功；接管前后容器ID、StartedAt和RestartCount均一致，原始配置文件SHA256未变。第二轮扫描仍只有一条记录且Version=1，容器状态指标不变。测试项目、容器与登记记录随后清理，临时helper无残留。

原有5个外部项目未被强行接管：实际列表已返回build依赖、Compose解析失败、配置不可读取等阻塞原因。不能据此声称所有现有项目已纳管；首版只自动接管能完整安全读取并通过既有规则的项目。Linux环境helperfs/runtime/handler测试通过；本轮Linux竞态重跑因Alpine包源TLS错误未完成，不拿旧批次竞态结果充当本轮结果。
