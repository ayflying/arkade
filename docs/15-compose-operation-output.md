# 编排执行日志统一窗口

启动、停止、重启、更新部署、拉取镜像、重建、删除、备份与保存部署统一使用异步操作任务。界面展示真实命令事件、标准输出、错误输出以及无单一命令的阶段标记，不编造百分比。多命令按实际执行顺序显示，第一步失败不得继续宣称后续步骤完成。

## 更新部署（deploy）与拉取镜像（pull）

两者不是同一个动作，界面上的主按钮是「更新部署」：

- **pull**：只执行 `docker compose pull`，容器仍跑旧版本。
- **deploy**：先判定有没有新版本，只有确实有更新才拉取并重建对应服务；没有可更新的镜像时**不拉取、也不重建任何容器**。判定流程、退化条件与"什么时候只能说不知道"见 [14-compose-pull-output.md](14-compose-pull-output.md)。

语义要点（与 `agent/internal/compose/deploy_test.go` 的断言一一对应）：

- 没有新版本时一条写命令都不执行，不会因为"点了一次更新"白停一次服务。
- 拉取失败立即停止，绝不用旧镜像继续重建；`up` 失败用本机原有镜像回滚一次，回滚失败如实报失败。
- 服务端回传 `updated_services`（机器可读的结论），界面不解析日志文本来判断结果。
- 任务进入终态后窗口底部显示完成横幅（成功「更新完成，如日志无异常再关闭此窗口！」/ 失败「执行失败，请先按上面的日志排查后再关闭此窗口。」），横幅只由任务状态驱动，与日志内容无关。

## 执行与配置边界

Agent调用原有Manager方法，保留项目互斥、哈希检查、原子写入、环境变量排除和超时语义，不为日志功能绕过原业务校验。旧同步接口继续兼容已有客户端。

Hub先将配置和请求幂等元数据放入同一事务，再向Agent发起任务。重试同一request_id不会重复保存、递增版本或另起操作；相同标识携带不同动作或配置会被拒绝。保存仍要求原version，省略env_content保留原值，空串才明确清除。操作用户不能借启动接口提交新配置。

创建、保存部署和删除要求manage，其他执行与日志读取至少operate。删除只有Agent成功且Hub记录ID/版本/哈希仍匹配时才删除记录，避免误删并发更新后的项目；不勾选删除卷时不会默认删除数据卷。配置同步标记同样需要版本和哈希匹配。

## 任务与日志

任务实际执行不依赖浏览器窗口保持打开；关闭窗口停止前端读取，不取消服务器任务。Hub后台只读跟踪终态完成必要的同步标记和条件删除；读取接口也幂等执行收尾。连接中断、记录过期与执行失败明确区分，不自动新建任务冒险重复执行。

服务端有界保留任务输出和元数据；截断有提示。密码与配置值不能写入命令输出或审计。脱敏无法可靠完成时隐藏相应输出，不能因为新增日志功能改变已授权部署的业务语义。命令以文本展示，不提供任意shell执行框。结构化探测命令（`ps`/`manifest`/`images`）的输出不进入日志，避免挤掉真正的失败信息。

## 验证约束

自动验收不得启动、停止、重建既有业务容器；生命周期动作应在独立fixture或假docker执行器验证。测试服部署仅更新Arkade管理组件。浏览器验收结束必须实际关闭测试网页和窗口，不只宣称会话已停止。
